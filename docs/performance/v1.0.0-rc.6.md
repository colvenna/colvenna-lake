# Colvenna Lake v1.0.0-rc.6 独立性能验收

## 1. 结论

`PASS`，即判定的运行 `rc6p` 的 `release.md` 的结论：判定的 43 行全部 PASS，没有 FAIL；另有 2 行只观测，不计入结论。路径表 26 行中 24 行 PASS、2 行只观测（OBSERVED）；检查表 19 行全部 PASS。

- 每条路径、每种变更的 p95 / p99 都在目标内，而且离目标很远。数据的路径：[Apache Paimon](https://paimon.apache.org/) 湖内的各层，以及查询引擎上的外表与物化视图（查询引擎是基于 [Apache Doris](https://doris.apache.org/) 4.1.4 的修改构建）。p95 最长的是源库 → DWS 看板，134 秒，目标 15 分钟；其余都在 49 秒以内。
- 固定看板查询：72,000 个样本，p95 0.069 秒、p99 0.089 秒；突发期间 p95 0.078 秒。目标 3 / 10 秒。
- 7 层都稳态（第 5.3 节）：后三分之一的积压 p95 比前三分之一至多高 0.0020 分钟（`dws_dashboard`；上限 0.5 分钟）；设上限的 4 层，整个窗口的最大积压离上限都很远，最近的是 ODS，0.603 / 5 分钟。
- 正确性、事件恰好一次、负载保持住（MySQL、[Apache Kafka](https://kafka.apache.org/) 与看板负载按时发出、日志完整）、看板查询没有出错、观测器、时钟与清理都 PASS。
- 看板运行的功能检查 19/19 PASS。`v1.0.0-rc.5` 在这一行 FAIL 的 `adhoc-bounded`（早期仓库的测试缺陷 #293）这次通过：修复（早期仓库的 PR #294，本候选里有）让采样先出样、再打开突发窗口，这次采样覆盖了整个窗口（第 5.4 节）。
- 本次没有因时钟作废的样本：MySQL 时钟读数往返的最大差是 655 毫秒，节点时钟的最大误差 9 毫秒（第 5.2 节）。

`rc6p` 是本候选的第一次、也是唯一一次性能运行，没有被拒绝或中止：开始之前，已经删除了 UAT 留下的开发用 Kafka（第 5.2 节）。

性能一项通过，不改变本候选的发布结论：本候选因产品缺陷 [#22](https://github.com/colvenna/colvenna-lake/issues/22) 是 NO-GO（见 [UAT 报告](../uat/reports/v1.0.0-rc.6/report.md)与[发布说明](../../release/v1.0.0-rc.6/notes.md)）。

本结论只适用于默认规模（写入 t3.xlarge、查询 r6i.xlarge 各 2 台）、下面这档负载与稳态。积压期不在范围内（第 8 节）。它不是容量上限。

## 4. 场景、方法与目标

| 负载 | 值 |
| --- | --- |
| MySQL CDC | 一张表，200 变更/秒：变更负载 184、看板运行的标记行 10、版本标记 3 × 2 |
| 版本标记 | 每秒 2 个键，每个插入、1 分钟后更新、2 分钟后删除；窗口内每种 14,429 个 |
| Kafka 事件 | 一张表，2,000 条/秒，每条 1,024 字节 |
| 看板 | 每秒 10 次固定看板查询、5 次内表点查、1 次交互点查；中段 20 分钟突发 |
| 时长 | 120 分钟，在 3 分钟预热之后 |

方法与 rc.5 的相同，按[性能测试第 1.3 节](../uat/performance.md#13-方法)（固定到本次测试的提交，即 tag），摘要：

- 每条路径按插入、更新、删除分别统计，各要至少 10,000 个有效样本，不足的只观测；
- ODS、DWD 逐键核对版本、校验和与删除；DWS 与 Doris 按前缀判定，删除要等聚合正确撤减；
- 稳态逐层判定：积压由版本标记与 Kafka 回执各自的确认与首次反映的时刻算出，不取样；窗口后三分之一的积压 p95 不比前三分之一高出 0.5 分钟以上，整个窗口的最大积压不超过从源端到这一层的路径的 p99 目标（DWD、DWS、ODS 上的物化视图没有这样的路径，不设上限）；
- DWS 与 Doris 的路径按设计三种变更的延迟相同；ODS、DWD 逐键量，同一时刻的三个操作通常落在同一个快照里；
- 每个样本比较的两个时钟，误差上限之和不超过 1 秒；
- 看板查询开环发出，响应时间从应发出算起；负载 Pod 是否按时发出另有检查（每组至多 1% 晚于 1 秒，日志完整），出错或没有发出的查询按从未返回计入；
- 看板运行的功能检查（不计被性能判定取代的行）都要 PASS。

`tests/performance/`（含 `perf.py` 与 `run-release.sh`）与 `tests/acceptance/dashboards/` 与早期仓库 rc.5 的 tag 上的逐字相同，只有看板运行的 `run-dashboards.sh` 多了 #293 的修复。[性能测试](../uat/performance.md)的内容与 rc.5 的相同，迁移到本仓库时只改了链接。

目标：[验收契约 2.1 节](../design/acceptance-contract.md#21-测量协议)的稳态 p95 / p99。

### 5.2 运行的前提与时钟

**独占环境。** `rc6p` 于 20:40:08 启动，20:40:11 的“环境是否独占”一步通过，20:40:39 开始了事件运行与看板运行，第一次就开始了。

UAT 的 kafka 阶段按[UAT 用例](../uat/cases.md)以 `KEEP_KAFKA=1` 保留开发用 Kafka，给后面的用例用。本次在 `us-west-2` 的 UAT、它单独的重跑与安全检查都结束之后、性能运行之前，先用 `tests/fixtures/kafka/dev-kafka.sh purge` 删除了它与它的数据（20:39:38 开始，20:40:08 "purged: no volume claim left"，证据 `uat-us-west-2/manual-purge-dev-kafka.log`）。

**时钟。** 各路径都没有作废的样本，以源库为起点的路径每种变更 14,429 个有效样本。

- 规则：MySQL 时钟的误差上限，是样本前后 90 秒内“MySQL 读数与 Pod 两次读数之差”的最大值，加上 Pod 所在节点的上限；两个时钟的上限之和超过 1 秒，样本就无效（[性能测试第 1.3 节](../uat/performance.md#13-方法)的“时钟”）。
- 本次 `layers.json` 记下的 `mysql_max_difference_ms` 是 655（rc.5 是 753）；节点时钟 `layers.json` 每组 108 次、`events.json` 每组 116 次测量，最大误差 9 毫秒，没有未同步的测量。

### 5.3 稳态

**规则。** 与 rc.5 的相同（早期仓库的 #268，从 rc.3 起生效）：

- 积压：一层在某一时刻的积压，是源端已确认、这一层还没有反映的最早那个变更已经等了多久。它由每个变更自己的两个时刻算出，不在格点上取样：湖内与 Doris 的层用版本标记，Kafka 用生产者的回执。
- 两条都满足才算稳态：窗口后三分之一的积压 p95（按时间加权）不比前三分之一高出 0.5 分钟以上；整个窗口的最大积压，不超过从源端到这一层的路径的 p99 目标。DWD、DWS 与 ODS 上的物化视图没有这样的路径，不设上限。
- 实现在 tag 的 [`tests/performance/perf.py`](../../tests/performance/perf.py)（函数 `backlog`、`backlog_bound`）。

### 5.4 看板运行的功能检查（#293 的修复）

看板运行的 `verdicts.tsv` 有 28 行，全部 PASS。计入“看板运行的功能检查”的是其中 19 行：被本次取代的 4 行性能判定（`load-within-targets`、`load-on-schedule`、`dashboard-under-burst`、`steady-state`）与看板运行自己测的 5 行新鲜度（`fresh-*`）不计，这 9 行也都 PASS。

**`adhoc-bounded`（早期仓库的 #293）。**

- 检查的内容与 rc.5 的相同：突发期间，ad-hoc 看板的 4 个用户各开 3 个连接、一个接一个地跑重查询（两个用户在看板自己的工作负载组，两个切到 Doris 的 `normal` 组）。每个组同时运行的查询不得超过上限 2，并且要真的跑到上限、有查询排队。同时运行数取 FE 自己的计数：采样 Pod 每秒两次执行 `SHOW WORKLOAD GROUPS`。判定要求采样覆盖整个突发窗口（第一个与最后一个样本离窗口两端都不超过 5 秒）。

## 7. 历史基线的适用性

与 rc.5 的基本相同：rc.3、rc.5 与本候选之间，Flink 与 Paimon（1.20.4 / 2.0.0）、CDC 连接器、测试 MySQL、EKS、节点、查询引擎镜像、负载与稳态的判定都没有变化。逐项的对照、差异与能否沿用，见 [rc.3 的性能验收](v1.0.0-rc.3.md)第 7 节：M1 的吞吐与延迟不沿用于默认规模，M1 的方法沿用；M3 的看板结论由本次的实测取代。

catalog 的形态有一处不同：它现在是 Colvenna Catalog 的发布版 `v1.0.0`，不再在本仓库构建。它的服务端从本仓库移植过去，HTTP 契约、配置名与指标名与原来的相同；本仓库没有逐项比对实现。M1 的基线用的是 JDBC catalog，本来就不沿用；所以这一处不同只影响与 rc.5 及以前各候选的比较（第 5.5 节），不影响历史基线的适用性。

## 8. 限制

- 积压期不在本 Release 的范围内：验收契约 2.1 的积压期目标（注入 10 分钟上游暂停，解除后 30 分钟内滞后回落到稳态 p95 以内）没有测。请求方 2026-10-22 定的口径只覆盖稳态。
- 稳态的盲区：增长按前后三分之一的 p95 判，余量 0.5 分钟，所以每小时增长慢于 0.75 ÷ 窗口的小时数 分钟的积压判不出（本次 120 分钟的窗口上 0.375 分钟/小时）。这是规则的余量，不是测量的限制。
- 默认规模之外没有验证：更多节点、M1 那档负载（CDC 1,000/秒、Kafka 10,000/秒）、24 小时连续运行。
- 测量的偏差：
  - 源端时间取提交之后 MySQL 的时钟，不早于真实提交，所以以源端为起点的延迟略为偏小；
  - Doris 路径的首次查到取查询结束的时刻，是保守上界；
  - 看板查询的响应时间包括新建连接，比连接池的客户端保守。
- 只观测的行：内表点查、外表交互点查，不计入结论。
- 只在一个区域（`us-west-2` 的 `uat`）运行，按清单的 `performance` 口径，性能验收不要求两个区域。
