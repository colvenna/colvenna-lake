# Colvenna Lake v1.0.0-rc.3 独立性能验收

## 1. 结论

`PASS`，即判定的运行 `rc3p` 的 `release.md` 的结论。发布检查的性能一项因此通过。本候选的发布结论另由 UAT 决定：必需用例有 FAIL，见 [UAT 报告](../uat/reports/v1.0.0-rc.3/report.md)。

- 每条路径、每种变更的 p95 / p99 都在目标内，而且离目标很远。
  - 数据的路径：[Apache Paimon](https://paimon.apache.org/) 湖内的各层，以及查询引擎上的外表与物化视图（查询引擎是基于 [Apache Doris](https://doris.apache.org/) 4.1.4 的修改构建）。p95 最长的是源库 → DWS 看板，123 秒，目标 15 分钟；其余都在 64 秒以内。
  - 固定看板查询：72,000 个样本，p95 0.073 秒、p99 0.105 秒；突发期间 p95 0.089 秒。目标 3 / 10 秒。
- 7 层都稳态，按本候选起生效的测法（第 5.3 节，#268，PR #274）：
  - 后三分之一的积压 p95 比前三分之一至多高 0.014 分钟（`materialized`；上限 0.5 分钟）；
  - 设上限的 4 层，整个窗口的最大积压离上限都很远：最近的是 ODS，0.609 / 5 分钟。
- 其余检查都满足：正确性、事件恰好一次、负载保持住（MySQL、[Apache Kafka](https://kafka.apache.org/) 与看板负载按时发出、日志完整）、看板查询没有出错、观测器、时钟、看板运行的功能检查（19/19）与清理。
- 以源库为起点的 3 条路径（9 行），每种变更各有 360 个样本因时钟作废（第 5.2 节）：一次 MySQL 的时钟读数往返至少 1.3 秒，作废了它前后 90 秒内的样本。有效样本各 14,069 个，仍高于 10,000，照常判定。

`rc3p` 是本候选的第一次性能运行，没有被拒绝或中止：开始之前，已经删除了 UAT 留下的开发用 Kafka（第 5.2 节）。

本结论只适用于默认规模（写入 t3.xlarge、查询 r6i.xlarge 各 2 台）、下面这档负载与稳态。积压期不在范围内（第 8 节）。它不是容量上限。

## 4. 场景、方法与目标

| 负载 | 值 |
| --- | --- |
| MySQL CDC | 一张表，200 变更/秒：变更负载 184、看板运行的标记行 10、版本标记 3 × 2 |
| 版本标记 | 每秒 2 个键，每个插入、1 分钟后更新、2 分钟后删除；窗口内每种 14,429 个 |
| Kafka 事件 | 一张表，2,000 条/秒，每条 1,024 字节，2 个分区 |
| 看板 | 每秒 10 次固定看板查询、5 次内表点查、1 次交互点查；中段 20 分钟突发 |
| 时长 | 120 分钟，在 3 分钟预热之后 |

方法按[性能测试第 1.3 节](../uat/performance.md#13-方法)（固定到本次测试的提交，即 tag），摘要：

- 每条路径按插入、更新、删除分别统计，各要至少 10,000 个有效样本，不足的只观测；
- ODS、DWD 逐键核对版本、校验和与删除；DWS 与 Doris 按前缀判定，删除要等聚合正确撤减；
- 稳态逐层判定：积压由版本标记与 Kafka 回执各自的确认与首次反映的时刻算出，不取样；窗口后三分之一的积压 p95 不比前三分之一高出 0.5 分钟以上，整个窗口的最大积压不超过从源端到这一层的路径的 p99 目标（DWD、DWS、ODS 上的物化视图没有这样的路径，不设上限）；
- DWS 与 Doris 的路径按设计三种变更的延迟相同；ODS、DWD 逐键量，同一时刻的三个操作通常落在同一个快照里；
- 每个样本比较的两个时钟，误差上限之和不超过 1 秒；
- 看板查询开环发出，响应时间从应发出算起；负载 Pod 是否按时发出另有检查（每组至多 1% 晚于 1 秒，日志完整），出错或没有发出的查询按从未返回计入。

目标：[验收契约 2.1 节](../design/acceptance-contract.md#21-测量协议)的稳态 p95 / p99。

### 5.2 运行的前提与作废的样本

**独占环境。** `rc3p` 于 11:11:39 启动，11:11:43 的“环境是否独占”一步通过，第一次就开始了。

UAT 的 kafka 阶段按[UAT 用例](../uat/cases.md)以 `KEEP_KAFKA=1` 保留开发用 Kafka，给后面的用例用。`v1.0.0-rc.2` 的第一次尝试 `rc2p` 就因为它还装着而被拒绝。本次在 `us-west-2` 的 UAT 结束（10:53Z）之后、性能运行之前，先用 `tests/fixtures/kafka/dev-kafka.sh purge` 删除了它与它的数据（10:57:40 "purged: no volume claim left"，证据 `uat-us-west-2/manual-purge-dev-kafka.log`）。

**作废的样本。** 以源库为起点的 3 条路径（MySQL → ODS、MySQL → Doris ODS 外表、MySQL → DWS 看板），每种变更各有 360 个样本作废，有效样本 14,069 个；其余路径没有作废的样本。

- 规则：MySQL 时钟的误差上限，是样本前后 90 秒内“MySQL 读数与 Pod 两次读数之差”的最大值，加上 Pod 所在节点的上限；两个时钟的上限之和超过 1 秒，样本就无效（[性能测试第 1.3 节](../uat/performance.md#13-方法)的“时钟”）。
- 本次：按 `dashboards/release/versions.log` 的读数，13:00:01Z 的一次版本标记调用（一个删除），这个差是 1,315 ms，所以这次调用从发出到收到回答至少 1.3 秒。它前后 90 秒内的样本因此无效：每秒 2 个键、180 秒，每种变更正好 360 个。
- 其余的调用里，这个差最大是 624 ms（紧接着的下一个，13:00:02Z），再往下 506 ms。
- `layers.json` 记下的 `mysql_max_difference_ms` 也是 1315；节点时钟的最大误差是 9 ms，没有未同步的测量。
- 这次调用为什么慢，证据里没有记录。

有效样本仍高于 10,000，这些行照常判定。版本标记按设计留出了约 30% 的余量给作废的样本，本次用掉 2.5%。

### 5.3 稳态（本候选起生效的测法）

**规则。** 按验收契约 2.1 节的稳态（源端积压不再增长），用[性能测试第 1.3 节](../uat/performance.md#13-方法)的测法：

- 积压：一层在某一时刻的积压，是源端已确认、这一层还没有反映的最早那个变更已经等了多久。它由每个变更自己的两个时刻算出，不在格点上取样：湖内与 Doris 的层用版本标记，Kafka 用生产者的回执。
- 两条都满足才算稳态：
  - 窗口后三分之一的积压 p95（按时间加权）不比前三分之一高出 0.5 分钟以上；

## 8. 限制

- 积压期不在本 Release 的范围内：验收契约 2.1 的积压期目标（注入 10 分钟上游暂停，解除后 30 分钟内滞后回落到稳态 p95 以内）没有测。请求方 2026-10-22 定的口径只覆盖稳态。
- 稳态的盲区：增长按前后三分之一的 p95 判，余量 0.5 分钟，所以每小时增长慢于 0.75 ÷ 窗口的小时数 分钟的积压判不出（本次 120 分钟的窗口上 0.375 分钟/小时）。这是规则的余量，不是测量的限制。
- 默认规模之外没有验证：更多节点、M1 那档负载（CDC 1,000/秒、Kafka 10,000/秒）、24 小时连续运行。
- 测量的偏差：
  - 源端时间取提交之后 MySQL 的时钟，不早于真实提交，所以以源端为起点的延迟略为偏小；
  - Doris 路径的首次查到取查询结束的时刻，是保守上界；
  - 看板查询的响应时间包括新建连接，比连接池的客户端保守。
- 以源库为起点的路径，一次 1.3 秒的慢调用作废了它前后 3 分钟的样本（第 5.2 节）；这 3 分钟里这几条路径的延迟没有被量到。
- 只观测的行：内表点查、外表交互点查与 Paimon → Doris 内表，不计入结论。
- #245 本次没有复现，它的根因仍没有新的证据（第 5.4 节）。
