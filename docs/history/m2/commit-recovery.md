# M2 REST 模式的原子快照提交与故障恢复

本页记录 Issue #19 的验收：多个写入方和维护任务经 cove-catalog 提交同一张表，同时注入以下故障：

- 服务实例切换；
- 元数据后端连接中断；
- 元数据后端拒绝连接；
- 全部副本同时失效。

验收看两点：快照发布是否有可验证的单一顺序；故障前后，元数据与 S3 文件的引用关系是否可核对。

提交协议和各故障的处理方式见 [cove-catalog LLD 的提交协议](https://github.com/colvenna/colvenna-catalog/blob/main/docs/design/colvenna-catalog-lld.md#提交协议)。所有资源都在 AWS profile `work`（账号 `<ACCOUNT_ID>`、区域 `us-west-2`），部署在 M1 PoC 集群上，只使用合成数据。部署方式见 [EKS 部署与引擎验收](catalog-on-eks.md)。验收不用 M1 的 JDBC 锁测试代替。

**证据的来源版本**：EKS 上的结果来自提交 `be3a644573d69733dbe6d41c248f1a7ea54db93b`，镜像以该 SHA 构建并安装。之后的提交只改了本页。原始日志在私有证据目录 `m2-19/run-be3a644/`。同目录下还有四次失败的运行，它们暴露的问题见 [过程中的发现](#过程中的发现)。

## 结论

| 接收条件 | 结果 | 依据 |
| --- | --- | --- |
| 已确认提交不丢失，未确认提交可判定最终结果；重试不产生重复业务效果 | **通过** | 720 次提交在故障中全部找到：每个已确认的提交恰好一次、行数齐全；12 次首次失败的提交都确定了结果，并经 `filterAndCommit` 安全重试，没有重复；1 次发布后响应丢失的提交被前滚（`ROLL_FORWARD_COMMIT`）。单元测试另外覆盖响应丢失、发布前后宕机和请求重放 |
| 冲突被拒绝或安全重试，读端只看到完整已发布快照 | **通过** | catalog 拒绝了 720 次旧基线上的提交（`COMMIT` `FAILED`，`committed=false`），写入方与维护任务都安全重试；读端 39 次读取（catalog 最新快照与最新 `snapshot-N` 文件交替），从未看到半个提交；两个冲突的 compaction 只发布一个（单元测试） |
| 故障前后元数据与 S3 文件引用关系可核对并有可恢复证据 | **通过** | 故障前后的一致性报告都干净；PostgreSQL 中已发布的提交意图恰好覆盖快照 1 到 725，每个一次，与指针一致；审计与提交意图的终态分布见下文 |

## 验证手段

### 写入方与读端：`CommitStress`

多个写入方各用自己的 `commitUser`，对一张 append 表编号提交，每次提交固定行数。提交失败时用 Paimon 的 `filterAndCommit` 重试：只有该用户、该编号的快照不存在时才提交，所以重试不会重复写入。

同时有一个读端，轮流读取两种"最新快照"，检查它只包含完整的提交、行数不倒退：

- catalog 发布的最新快照；
- 目录里编号最大的 `snapshot-N` 文件，即流式读端发现新快照的方式。

读取失败一律记为违例，只有 catalog 本身不可达或返回 5xx（故障期间）除外，这类失败单独计数。

运行结束时检查四项：

- `every-commit-once`：每个已确认的提交恰好出现一次，行数齐全；表中没有从未写过的提交；
- `every-outcome-known`：每个提交的最终结果都已确定，`UNRESOLVED` 为 0；
- `readers-see-whole-commits`：读端从未看到半个提交；
- `snapshot-ids-contiguous`：仍保留的快照 id 连续，没有空洞。维护任务会过期旧快照，所以完整的顺序由下文 PostgreSQL 中已发布的提交意图核对。

### 维护任务：`MaintenanceLoop`

与写入方并行，经同一个 catalog 循环执行 compaction 和快照过期，让 compaction 提交与写入方的追加互相竞争。故障期间某一轮失败是允许的；故障结束 60 秒后的每一轮都必须成功。

经 REST 的提交是乐观的，靠 compare-and-set 排序。写入方每几百毫秒提交一次，而 compaction 每次重试都要重新规划，约需一秒，所以总在比较时落后，按 Paimon 默认的 10 次重试会放弃。维护任务因此给 compaction 设了 200 次、间隔 50 毫秒到 0.5 秒的快速重试。这也是多写入方共存时维护作业应有的配置。

### 一致性核对：`GET /cove/admin/v1/consistency/{db}/{table}`

仅限管理员，核对内容见 [LLD 提交协议一节的一致性核对](https://github.com/colvenna/colvenna-catalog/blob/main/docs/design/colvenna-catalog-lld.md#提交协议)。报告同时给出核对前看到的指针与未完结意图，以及解决之后的状态。

### 单元测试（真实 PostgreSQL 与本地文件系统）

`CommitProtocolTest` 覆盖：

- 并发写入不丢提交；
- 两个服务实例上的写入方不丢提交；
- 提交响应丢失后只生效一次；
- 发布后宕机由下一次访问前滚；
- 发布前宕机不留快照，重试成功；
- 重放的提交请求幂等；
- 已关闭意图的迟到写入、catalog 之外写入的快照都会围栏该表；
- 被删后重建的表不接受旧写入方；
- 超时的意图被关闭；
- 两个 compaction 从同一基线合并同一批文件：catalog 拒绝后到者在旧基线上的提交，后到者随后发现冲突并放弃，只有一个 compaction 被发布，数据不变。

`ConsistencyCheckTest` 覆盖：

- 干净的表报告一致，并给出核对前的状态；
- 缺失的数据文件、未发布的快照被列为问题；
- PostgreSQL 中快照或 schema 的副本与文件不符时被列为问题；
- manifest 丢失时记为问题而不是报错；
- 只有管理员能调用。

## EKS 上的故障注入

`infra/m2/scripts/run-commit-faults.sh`：

- 6 个写入方，每个提交 120 次、每次 500 行、间隔 3 秒；
- 维护任务每 20 秒一轮，持续 25 分钟，比全部故障结束得更晚；
- catalog 两个副本。

表中已有至少 5 个已发布快照、一致性报告为干净时才开始注入故障，并要求每次注入时写入方仍在运行。依次注入：

| 故障 | 做法 | 生效的证明 |
| --- | --- | --- |
| 1. 实例切换 | 强制删除一个副本，30 秒后删除另一个原副本 | 两个副本都被替换 |
| 2. 元数据连接中断 | 30 秒内每 3 秒终止 catalog 角色在 PostgreSQL 上的其他会话 | 终止的会话数大于 0 |
| 3. 元数据后端拒绝连接 | 数据库属主把 `cove_catalog` 设为不接受连接（`ALLOW_CONNECTIONS false`），并终止已打开的连接，40 秒后重新开放 | 期间就绪副本数降到 0（就绪探针检查数据库连接）；记录重新开放后多久恢复服务 |
| 4. 全部副本失效 | 同时强制删除两个副本 | 两个副本都被替换 |

结束后必须同时满足：

- 写入方的四项检查通过，且至少有一个提交首次失败后才确定结果，即故障确实打到了进行中的提交；
- 审计中有 catalog 拒绝的旧基线提交（`COMMIT` `FAILED`、`committed=false`），且这些提交已由写入方安全重试；
- PostgreSQL 中已发布的提交意图恰好覆盖快照 1 到 N，每个一次，N 是指针；
- 故障结束 60 秒后的维护轮次全部成功；
- 一致性报告干净。

另外从 PostgreSQL 汇总两项，作为证据：期间的审计事件，按动作、结果、状态码分组；提交意图的终态分布。

## 过程中的发现

前四次运行失败，暴露了以下问题，都已修复：

- **compaction 跟不上写入方**：经 REST 的提交是乐观的。6 个写入方每几百毫秒提交一次，compaction 每次重试都要重新规划约 1 秒，总在比较时落后，Paimon 默认的 10 次重试用完就放弃，维护任务一轮都没成功。现在给 compaction 设了 200 次快速重试，见 [维护任务](#维护任务maintenanceloop)。多写入方共存时，维护作业都应这样配置。
- **一致性报告太慢**：报告原先核对每个保留快照的数据文件，表有 720 个快照时，一次请求要几分钟。现在核对最早、最新与均匀抽取的共 20 个快照，再加每个 tag。
- **网络策略会干扰故障本身**：最初用出站 NetworkPolicy 切断 catalog 到数据库的连接。删除策略之后，这个集群的 CNI 让 catalog 的 JVM 在 9 到 15 分钟里无法解析域名，而同一 Pod 里的 `getent` 却能正常解析。这样测到的是 CNI，不是 catalog，所以改为在数据库侧拒绝连接。
- **基线报告要避开进行中的提交**：报告针对静止的表。写入进行中取的基线，会把正在提交的快照报成超出指针，所以基线改在两次提交之间取。
