# Security

Colvenna Lake 1.0.0 is its first release, promoted from the release candidate `v1.0.0-rc.7` without a rebuild ([release notes](release/v1.0.0/notes.md)). Security fixes are made for the latest release only. A fix is made on `main` and ships in a new patch release (1.0.1, then 1.0.2, ...), accepted and promoted from its own release candidate as 1.0.0 was ([release candidates](release/README.md#晋升), in Chinese). A release never changes once made: its tag never moves, so an earlier release, and any release candidate, does not get the fix. Colvenna Lake's images are not published: build them from the release's tag ([install manual](docs/manual/install.md)).

Upgrades in 1.x: a release upgrades an environment in place, keeping its data, by `deploy/install.sh` run again from the release's tag ([install manual](docs/manual/install.md#7-升级), section 7), and its candidate's UAT runs that upgrade (UAT-DEP-06). Its release notes name any step of its own. Going back to an earlier release, and an upgrade that skips a release, are not tested.

The deployment's security points are in the [install manual](docs/manual/install.md#6-安全要点), and the exposed surfaces with how each is protected are in [section 12.1 of the High-Level Design](docs/design/hld-realtime-lakehouse.md#121-边界与威胁模型) (both in Chinese).

## Reporting a vulnerability

Do not put passwords, tokens, keys, cloud credentials, deployment values (account IDs, domains, ARNs, internal addresses) or exploit details in an ordinary issue or pull request.

Secrets are scanned for with ggshield, GitGuardian's command-line scanner: nothing is published, no release and no change of the repository's visibility, before a scan of the repository's history, its release assets, its workflow artifacts and its GitHub text finds 0 incidents. Local hooks scan each commit and each push as a best effort, and CI scans each push and pull request again. [`.gitguardian.yaml`](.gitguardian.yaml) lists each value checked by hand and found not to be a credential, by hash only, and each addition to it is reviewed in its pull request; a real credential is revoked or rotated, never ignored. See [CONTRIBUTING.md](CONTRIBUTING.md#secret-scanning).

For a confidential report, use GitHub's private vulnerability reporting: **Report a vulnerability** on the repository's [Security tab](https://github.com/colvenna/colvenna-lake/security). Only the reporter and the maintainers see the report. Name the affected component, the release or commit, and the steps to reproduce. A vulnerability in the catalog server itself goes to [Colvenna Catalog](https://github.com/colvenna/colvenna-catalog/security).

## Security model in brief

- **No anonymous public entry.** Every service or resource reachable from outside the cluster requires authentication; IAM authentication (SigV4, EKS access entries, IRSA and STS credentials, presigned URLs) counts. The EKS API requires IAM authentication and admits only the installer's address. Lambda function URLs are never used. After an install, `tests/acceptance/security/inventory.sh` lists the publicly reachable resources of the account in that region and checks that there is no Lambda function URL and no anonymous public resource, and `tests/acceptance/security/run-denials.sh` checks that unauthenticated, over-privileged and entry-bypassing requests are refused ([install manual, section 6](docs/manual/install.md#6-安全要点)).
- **Authenticated web entry.** The management console and the BI interface sit behind a public Application Load Balancer with an ACM certificate, TLS 1.2/1.3 only, HTTP redirected to HTTPS. Every forwarding rule first signs the user in with Amazon Cognito: no self sign-up, TOTP MFA required. The applications verify the ALB-signed claims and the Cognito access token, and roles come only from the user pool's groups ([HLD 12.1](docs/design/hld-realtime-lakehouse.md#121-边界与威胁模型), [web entry and console LLD](docs/design/colvenna-console-lld.md)).
- **colvenna-catalog tokens.** The catalog has a ClusterIP only, serves TLS from its own private CA, and admits client namespaces by label. Clients present opaque Bearer tokens: a `colvenna_` prefix and 32 random bytes, returned once at issue. The server stores only their SHA-256 with the principal, the expiry and a revocation flag; tokens expire (90 days by default, at most 400) and can be revoked, which takes effect within the authentication cache's lifetime (2 seconds by default). Per-table data credentials already issued stay valid until they expire (3 hours by default) ([catalog LLD, authentication and audit](https://github.com/colvenna/colvenna-catalog/blob/v1.0.0/docs/design/colvenna-catalog-lld.md#认证与审计), [per-table data credentials](https://github.com/colvenna/colvenna-catalog/blob/v1.0.0/docs/design/colvenna-catalog-lld.md#按表数据凭证), in Colvenna Catalog's repository at the release Colvenna Lake pins).
- **Least privilege.** Each IRSA role trusts only its own service account. Each managed namespace has its own job role, which reaches only that namespace's Flink state. Engines read and write table data only with per-table temporary credentials: colvenna-catalog issues them for Paimon tables, Apache Polaris for Iceberg readers ([install manual, section 6](docs/manual/install.md#6-安全要点)).
- **Secrets.** Passwords and tokens go only into Kubernetes Secrets or AWS Secrets Manager, never into custom resource manifests, and the scripts do not print them. The warehouse bucket blocks public access, requires TLS and is encrypted at rest. ([HLD 12.1](docs/design/hld-realtime-lakehouse.md#121-边界与威胁模型), [install manual, section 6](docs/manual/install.md#6-安全要点))
- **Known limits.** These are the ones the [HLD's boundary table (12.1)](docs/design/hld-realtime-lakehouse.md#121-边界与威胁模型) and [12.2](docs/design/hld-realtime-lakehouse.md) record; the HLD is the full list.
  - Marquez and Prometheus do not authenticate and are protected only by NetworkPolicy; whoever can reach Marquez's API can write lineage.
  - colvenna-catalog's `/metrics` (port 9100) does not authenticate; NetworkPolicy admits only namespaces labelled for monitoring.
  - The Flink REST endpoint does not authenticate clients: it is reachable only through `kubectl port-forward`, and whoever can reach it administers the jobs.
  - The project's PostgreSQL instance also holds the metadata databases of Marquez, Polaris and Superset, each with its own database and role; its security group admits the database port from the whole cluster security group, not per component.
  - In-cluster connections to the query engine use the MySQL protocol without TLS, and the query engine's privileges do not apply to its `root` and `admin` accounts, which are kept for operations.
  - Per-table credentials bound object paths, not columns or rows.
